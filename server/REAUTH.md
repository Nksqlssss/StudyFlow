# Email reauthentication

This is proof of access to the current verified mailbox, not fresh Google
authentication. Google OAuth login/linking and its ID-token validation are unchanged.

## Authentication and session binding

Every endpoint below requires `Authorization: Bearer <JWT>` for an existing user
with `emailVerifiedAt != null`, and JSON where a body is specified. Missing,
invalid, expired or revoked JWTs return **401** `{ "message": "Unauthorized" }`.
An unverified account returns **403** with `code: EMAIL_NOT_VERIFIED`.

Use the exact same JWT throughout request, verification and action consumption.
Session binding is HMAC-SHA-256 of that credential with a domain-separated server
key; the original JWT is never stored. New JWTs include random `jti` values so two
logins in one second are separate sessions. Existing unrevoked JWTs remain accepted.
Signing-key rotation invalidates JWTs and pending OTP bindings.

Supported purposes: `set_password`, `change_email`. Grants cannot change purpose,
user, session or verified email. Account deletion cascades all related rows.

## POST /auth/reauth/email/request

```json
{ "purpose": "set_password" }
```

Success **200**:

```json
{ "message": "Verification code sent", "expiresIn": 600, "retryAfter": 60 }
```

The only accepted input is purpose. Destination addresses, user IDs and other
fields are rejected. The destination is read exclusively from verified `User.email`.
Code: six decimal digits generated by `crypto.randomInt`, including leading zeros.
Only a keyed HMAC of the code and its user/session/purpose/email/random-nonce context
is stored, not the raw code or a cheaply enumerable unkeyed digest. TTL: 10 minutes.

There is one current challenge per user, across all sessions and purposes. A new
allowed request replaces it, but does not reset abuse counters. Issued grants stay
valid until their own expiry, consumption, email change or session revocation.

Limits enforced in PostgreSQL under a per-user transaction lock:

- At least 60 seconds between sends.
- At most 3 sends per 60-minute fixed window beginning with the first send.
- At most 5 incorrect, expired, reused, wrong-purpose or wrong-session code
  attempts per 15-minute fixed window. At exhaustion only reauthentication is
  temporarily blocked; ordinary account login is not locked.
- Switching IP, session or purpose does not reset these counters.
- Provider failures consume send budget and invalidate only that challenge.

Additional IP rate limit: 10 requests/minute. No code is returned in the response.
For `set_password`, an account with an existing password receives **409**
`PASSWORD_ALREADY_SET` before mail is sent.

## POST /auth/reauth/email/verify

```json
{ "purpose": "set_password", "code": "123456" }
```

Send code as a six-character string, not a number. Success **200**:

```json
{ "reauthToken": "64-lowercase-hexadecimal-characters", "expiresIn": 300, "purpose": "set_password" }
```

The token contains 32 cryptographically random bytes. Only SHA-256 of this high
entropy secret is stored. Its lifetime is 5 minutes, capped by JWT expiry.
Verification atomically consumes the code and creates one grant. Concurrent verify
calls can issue at most one grant. Comparisons use a timing-safe HMAC comparison.
Failed-attempt counters commit even when verification fails.
Additional IP limit: 20 requests/minute.

## POST /auth/password

```json
{ "password": "a-new-password", "reauthToken": "one-time-set_password-proof" }
```

Password: 8-72 characters, same policy as the existing endpoint. Success: **204**.
This installs only the first password. It atomically consumes a valid `set_password`
grant and stores a bcrypt hash. Missing proof returns **403**
`REAUTHENTICATION_REQUIRED`; invalid/expired/foreign/reused proof returns **403**
`INVALID_REAUTH_TOKEN`; an existing password returns **409** `PASSWORD_ALREADY_SET`.
Malformed bodies return **400** `VALIDATION_ERROR`. IP limit: 5 requests/minute.

Existing `PATCH /auth/password` still requires `{ currentPassword, newPassword }`.
It does not accept an OTP as a substitute for that check.

## POST /users/me/email/change

Choose exactly one method:

```json
{ "newEmail": "new@example.com", "currentPassword": "current-password" }
```

```json
{ "newEmail": "new@example.com", "reauthToken": "one-time-change_email-proof" }
```

Success remains **200** `{ "message": "Confirmation email sent", "expiresIn": 1800 }`.
Passwordless users must obtain email proof; password users may choose either.
The grant is atomically consumed with creation/replacement of the email-change
token. A validation/uniqueness failure rolls consumption back. If sending the new
email fails after commit, the grant stays consumed: obtain a new proof to retry.
Using both methods is **400** `VALIDATION_ERROR`. Missing usable proof is **403**
`REAUTHENTICATION_REQUIRED`; invalid proof is **403** `INVALID_REAUTH_TOKEN`.
The remaining contract is documented in [EMAIL_CHANGE.md](EMAIL_CHANGE.md).

`POST /users/me/email/confirm` stays `{ token }` plus Bearer authentication. Its
email-link format, success response and verification requirements are unchanged.
It also invalidates codes/grants for the previous address, including if that
address is later restored. `OAuthAccount.email` is never changed by this flow.

## POST /auth/logout

No body required. Success: **204**. Revokes the exact current JWT until its expiry,
deletes its grants and invalidates its pending code. Other sessions are unaffected.
Expired revocations for this user are pruned on logout. All existing protected
routes check revocation. Reusing that JWT, including another logout, returns **401**.

The frontend calls this endpoint before removing the JWT locally, and clears
local session data even if the request fails. A warning distinguishes local-only
logout from confirmed server revocation. LocalStorage removal alone is invisible
to the server and cannot revoke a copied credential or its grants.
Requests already in flight can finish as with normal concurrent HTTP operations;
reauthentication mutations and logout serialize through the same per-user lock.

## Error response contract

Reauthentication application errors use `{ "code": "...", "message": "..." }`.

| Status | Code | Meaning |
| --- | --- | --- |
| 400 | VALIDATION_ERROR | Malformed body, unknown fields, purpose or code format |
| 400 | INVALID_REAUTH_CODE | Invalid, expired, used, foreign or wrong-session/purpose code |
| 403 | EMAIL_NOT_VERIFIED | Current mailbox is not verified |
| 403 | REAUTHENTICATION_REQUIRED | Action requires proof |
| 403 | INVALID_REAUTH_TOKEN | Wrong user/session/purpose/email, expired or used grant |
| 409 | PASSWORD_ALREADY_SET | Password creation is no longer applicable |
| 429 | REAUTH_SEND_LIMIT | Per-user cooldown or hourly send limit |
| 429 | REAUTH_ATTEMPTS_EXCEEDED | Per-user failed-attempt budget exhausted |
| 429 | RATE_LIMITED | Additional IP limit on reauth routes |
| 503 | EMAIL_DELIVERY_FAILED | Provider delivery failed |
| 503 | REAUTH_UNAVAILABLE | Unexpected failure; details are not exposed |

Per-user 429 responses include `retryAfter` seconds and a `Retry-After` header.
IP limits on existing action routes retain their existing Fastify response format.
Malformed code formatting is rejected before the guessing counter; it cannot
match any valid code and is still subject to the IP limit. Without a current
challenge, verify returns 400 and cannot issue any grant.

## Frontend sequence

1. Keep the current JWT. Request a code for the intended purpose.
2. Ask for the emailed six-digit code. Preserve leading zeros.
3. Verify with the same JWT and purpose.
4. Hold `reauthToken` only in memory and immediately send it with the action.
5. Do not put codes, grants or JWTs in URLs, analytics, errors or logs.
6. Email changes then require the existing confirmation link sent to the NEW
   address. The OTP is sent to the CURRENT address; these are different steps.
7. On logout call the server endpoint, then clear frontend auth and local data.

The shared `AccountSecurity.svelte` component connects these steps on Profile and
Settings using the existing modals. Codes, passwords and grants stay in component
memory and are cleared when the modal closes. Responses from a closed flow or an
old auth session cannot update the current interface.

Pending Google linking is also bound to the initiating session hash. A Google
callback after server logout cannot finish linking, even if its state cookie has
not expired. Apply `20261023133000_bind_google_link_session` for this binding.

## Deployment and checks

Apply migrations before starting the updated server:

```sh
cd server
npx prisma migrate deploy
npx prisma generate
npm run typecheck
npm run build
npm test
```

No dependency was added. Existing JWT_SECRET keys the domain-separated HMACs;
keep it secret. Existing Resend configuration and sender are reused. The default
`onboarding@resend.dev` sender has provider restrictions: configure a verified
sender/domain before production delivery to arbitrary addresses.

Tests use real PostgreSQL in disposable schemas, never reset the main database,
and inject email senders instead of sending live mail. Counters are bounded to one
challenge row/user. Expired grants are pruned on code request; user revocations on
logout. Inactive users' expired security rows may remain until a scheduled
maintenance cleanup or user deletion; no background job is introduced here.
